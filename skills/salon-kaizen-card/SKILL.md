# 改善问题卡（丰田 CI · 单店改善）

> 知识来源：`knowledge/shiny-ci-dbs-v1/core.md`（模型 1 单店改善闭环、模型 5 三类指标）
> 指标库与根因候选：`../salon-strategy-advisor/reference.md`（第 1、2 节）。选指标、列根因之前先读。
> 同系列技能：试点结束后用 `salon-pilot-review` 复盘；议题涉及多个问题或属于战略层面时，改用 `salon-strategy-advisor`。

**一张卡只写一个问题。** 用户一次说了多个问题时，按以下顺序只取第一个：影响顾客体验或服务质量的 → 主要经营瓶颈 → 能较快看到结果的。其余问题列在卡片末尾"待处理"。

## 改善闭环
顾客价值 → 现场事实与现行标准 → 识别差距 → 验证根因 → 小范围试验 → 检查结果与副作用 → 更新标准与培训 → 持续复查

## 填写流程
1. **问题定义**：从顾客视角写，必须能观察、能计数。
   ❌"服务不好" → ✅"预约顾客在约定开始时间之后的可避免等待"
2. **为什么现在优先**：一句话说明它对顾客、质量或经营瓶颈的影响。
3. **现场事实**：分三栏写：已知事实（带口径）、用户的猜测、未知项。缺的数据写成数据需求清单（字段、来源、谁收集、几天）。**不编造数字。**
4. **现行标准**：目前有没有标准？版本号是什么？员工实际是怎么做的？没有标准本身就是一条发现。
5. **根因假设**：写 1 个主假设，加至少 1 个备选解释，并写明每个假设用什么现场观察或数据来验证。**不接受"员工态度差"作为根因**，要先查流程、标准、负荷和工具。
6. **试点设计**：
   - 范围：只选一家店、一个项目或一个班次
   - 负责人、起止日期
   - 具体改变了什么（员工看完就能照做）
7. **指标**（三类都要有，每类 1–3 个，写清口径）：
   - 过程指标：新做法有没有被执行
   - 结果指标：顾客或经营结果有没有变好
   - 保护指标：有没有靠拒接顾客、缩短服务、加班、强推换来表面改善
8. **复盘日期**：按指标的观察窗口定。复购这类慢指标要等完整窗口，写明"到期前不下结论"。
9. **成功后的去向**：更新哪份标准、谁来培训、第二家店独立试用的条件。

## 输出格式
```
# 改善问题卡：<问题名>
- 问题定义：
- 为什么现在优先：
- 现场事实：已知 / 猜测 / 未知
- 数据需求清单：
- 现行标准：
- 根因假设：主假设（验证方法）/ 备选解释（验证方法）
- 试点：范围 / 负责人 / 起止日期 / 具体做法
- 指标：过程 / 结果 / 保护（含口径）
- 复盘日期：
- 成功后：标准更新 / 培训 / 第二家店条件
- 待处理的其他问题：
```

## 检查清单
- [ ] 问题定义能观察、能计数
- [ ] 至少有 1 个备选解释
- [ ] 三类指标齐全，保护指标能抓住"作弊式改善"
- [ ] 试点范围足够小
- [ ] 没有编造数字，缺失的数据都进了需求清单
